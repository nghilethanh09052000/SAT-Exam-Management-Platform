# App Audit Handoff — 2026-05-20

Purpose: current-state snapshot after a fresh pass through the app routes, API routes, Supabase migrations, and visible product flows.

## Overall State

The project is a working internal alpha for a Vietnamese SAT management platform.

Core loop currently exists:

- Admin manages students, staff users, courses, imports, and device sessions.
- Teacher manages courses, classes, weeks, students, questions, uploads, assignments, exam papers, and assignment results.
- Student sees course-grouped assignments, starts a Bluebook-style test, autosaves work, submits, sees results when allowed, and reviews an error log.
- Supabase migrations and RLS policies exist.
- A separate `pipeline/sat-pipeline` project exists for scraping/exporting SAT question content.

Current priority direction: admin and teacher features first. Student feature expansion can wait unless it blocks admin/teacher workflows or test-taking reliability.

### P0: Attempt creation race

Status: closed in code.

Implemented:

- `create_submission_attempt(p_instance_id UUID)` database RPC.
- Transaction-scoped advisory lock keyed by instance and student.
- Deadline, published state, active student enrollment, and attempt-limit checks inside the database function.
- Student test page and `/api/submissions` use the RPC.

Deployment risk:

- Every local/staging/production Supabase environment must apply migrations `00026` and `00027`.
- If the RPC is missing, students cannot start a first attempt. This happened locally and was confirmed by checking `pg_proc`.

### P1: Current active bug — stale Jest retry tests

Status: active.

What changed:

- Code now treats `assignment_instances.max_retakes` as maximum total attempts.
- `lib/utils/submission-rules.ts` returns `Math.max(1, maxRetakes)`.
- Migration `00027_treat_max_retakes_as_total_attempts.sql` updates the RPC to the same total-attempt semantics.

Bug:

- `__tests__/utils/submission-rules.test.ts` still expects the old behavior where `max_retakes = 2` means 3 total attempts.

Impact:

- `pnpm exec jest --runInBand` currently fails 2 assertions.
- Product behavior appears internally aligned with the newer label “Số lần làm bài tối đa,” but the test needs updating.

Recommended fix:

- Update the test names and expectations:
  - `getMaxAttempts(0) === 1`
  - `getMaxAttempts(2) === 2`
  - `canCreateAttempt(1, 2) === true`
  - `canCreateAttempt(2, 2) === false`

### P1: Device-session behavior needs browser QA

Status: implemented, needs QA.

Current behavior:

- Middleware assigns `gd_device_session_token`.
- Student second-device access redirects to `device_limit`.
- Admin can clear all device sessions for a user.

Potential bugs:

- Middleware-created session rows depend on service-role env vars being available.
- Device sessions are platform-level records, not Supabase Auth session revocation. A blocked browser is signed out by the login page, but this should be QA’d across Chrome/Safari/private windows.
- Teachers/admins are tracked but not blocked by one-device enforcement.

### P1: Submission integrity and deadline enforcement

Status: partially covered.

Covered:

- Attempt creation checks deadline in RPC.
- Submission ownership and in-progress status are checked before submit.

Potential bugs:

- `/api/submissions/[id]/submit` does not re-check assignment deadline at submit time.
- It trusts the client-provided answer list length for `total_questions`.
- It does not verify every submitted question belongs to the assignment instance.
- It uses service-role writes after initial ownership check; logic should remain tight here.

Recommended fix:

- Fetch assignment question IDs for the submission’s instance inside submit route.
- Reject answers for questions outside that assignment.
- Use assignment question count for `total_questions`.
- Re-check deadline unless late submission is intentionally allowed.

### P1: Shuffle flags are stored but not fully applied

Status: active.

Current behavior:

- Assignment instance stores `shuffle_questions` and `shuffle_options`.
- Student test page sorts assignment questions by order and options by order.

Potential bug:

- Teachers may expect shuffle settings to affect student delivery, but the student payload currently ignores them.

Recommended fix:

- Apply deterministic per-submission shuffle so refreshes do not reorder unexpectedly.
